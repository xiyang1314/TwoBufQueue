1 MiB 发送后，业务尾延时为什么升高？

主要证据指向：发送期间换核，预热的业务数据不在新核的 L1 中，随后的随机链式访问需要等待缓存数据。少数这样的窗口足以拉高 p99、p999。

2026-10-12 · Apple M3 / macOS 14.4.1 · Clang 18.1.8 -O3 · 高 QoS，未硬绑核。本页是原因诊断，不替换完整性能报告。

测试条件

消息 32 B每次发送 1 MiB第一层 16 KiB第二层 256 MiB业务数据 48 KiB

第一层为 4 × 4 KiB；第二层为 65,536 × 4 KiB。普通 write、publishMAX、不扫描 current、保留原来的写后 volatile 首字节读取。各队列回调均执行 64 次循环并校验全部消息、全部字节和 FIFO。

业务每次查询访问并修改 8 个随机链接节点。发送前执行 512 次预热；发送后立即测 64 次查询，分成 4 组，每组 16 次。每类每轮 2,500 个发送窗口，共 10,000 个计时组，运行 3 轮。每轮正式消息数 81,920,000 条；队列与消费线程持续工作，积压目标约 80%。

p50 / p99 / p999 是 16 次查询的平均 ns/次的分位数，先按每轮 nearest-rank 计算，再取三轮均值；不是单次查询、也不是消息从写入到回调的延时。

第三条证据：相同线程、相同机器码，仅改变预热数据归属

不使用队列。两个测量分支都由同一个 worker 执行相同 Business::step。一个分支由 worker 自己先预热并修改全部业务数据；另一个分支由另一核上的线程预热并修改，再交给 worker。预热和握手不计入查询耗时。

为什么几条访存指令能让尾延时差这么多？

CPU A 预热业务数据进入 A 的 L1，修改后的数据由缓存一致性协议维护。
→
发送期间换核线程转到 CPU B；A 的私有 L1 不会随线程一起搬过去。
→
业务恢复执行B 上的链式 load 等待数据；下一节点地址还依赖前一节点的 next。
add x9, x12, x9, lsl #6   // 根据当前节点编号形成地址
ldr x13, [x9, #8]         // 读取节点 value
eor / ror / add           // 更新业务状态
str x8, [x9, #8]          // 修改 value，产生脏数据
ldr w9, [x9]              // 读取 next，决定下一个节点地址
... 下一轮 add / ldr

当 next 的 load 未命中时，下个随机地址还不知道，处理器很难提前发出后续整条访问链。代码和指令数量不变，但等待周期变多。这里没有在计时业务中调用 write；复制和回调仍在其他线程继续执行。

“L1 脏数据回写”指修改过的缓存行从 L1 向共享 L2 写回，不能等同于每次都写到了 DRAM。另一个核访问数据还涉及缓存一致性和读写权限；未命中也可能由其他缓存层满足，不能把所有 L1 未命中都称为“访问内存”。

本机这次取得的是窗口硬件事件 + 精确汇编 + 相同机器码控制实验；没有取得带地址的逐条指令延时轨迹，因此不能把某一条 ldr 的单次延时直接标成固定的多少 ns。

针对迁移这一原因，更直接的办法是在支持的平台把整条热路径线程（业务 + write）固定到同一物理核，并避开复制、回调和其他重任务。现有 producer_cpu 可供支持的平台使用；本机 macOS 不支持按 CPU 编号硬绑核，实测 THREAD_AFFINITY_POLICY 返回 46（service not supported），高 QoS 也不能保证不迁移。这里没有拿其他平台的绑定效果充当已实测结果。

硬绑核可以消除换核这一部分原因，仍不能消除中断、抢占和内核执行。在最慢的少量 p999 样本中，也观察到指令数、内核时间增加；例如一组指令从通常 3,007 升到 10,780，内核时间从 83 ns 升到约 2,417 ns。仅优化队列内存占用无法保证消除这部分。
