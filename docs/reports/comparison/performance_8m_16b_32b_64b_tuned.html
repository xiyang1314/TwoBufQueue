本页只测试16、32、64 B。每种长度完整遍历270组TwoBufQueue参数和每种开源队列9组参数，共891组；每组先校验一千万条完整字节和FIFO，再分别测吞吐与分组耗时，每项5次。最后候选把三种长度和各队列交错复测，保留全部测量，未剔除异常值。

每层消息数据区严格8 MiB，合计16 MiB；块大小64 KiB/256 KiB/1 MiB/2 MiB/4 MiB，分别配128/32/8/4/2块，池不增长，至少2块。块和队列管理元数据、计时前准备的输入不计入消息数据区；这个预算不等于进程RSS。

全过程关闭当前块扫描，发布批次为UINT32_MAX，业务回调循环为0，两层复制与独立回调线程保留。每轮写入约6.4 MiB，尾块交接和等待回调在发送计时之外。高QoS，接电源，未硬绑核。

优化、对照与尚未解决的差距

已确认的实验事实与尚未确认的硬件原因分开描述。

本次生产代码只采用一项可选优化：MAX发布模式增加线程私有的剩余容量计数。普通写入检查剩余容量、复制、推进本地指针；结束状态、申请和换块检查集中到冷路径。成功取得块后，编译器使用已有“地址非空”不变量消除重复返回值判断。默认关闭，通过Writer最后一个模板参数选择，不增加逐条运行时开关。

容量计数在finish、finish_block和交接失败时归零，防止继续使用已交出的块；flush仍发布已复制完成的本地指针。普通发布策略、同步回调、长度编码与数据复制方式保持原有行为。Writer和SeqWriter均支持此策略。

16 B异常可重复，改善也可重复，但没有完全解决：关闭当前扫描的旧实现同条件复测，batch=32约1078 M条/s，MAX约577 M条/s；新的MAX容量计数版本同条件约911 M条/s，最终调参约948 M条/s。MAX最优p50约0.792 ns，低于此前有限批次报告约0.908 ns；吞吐仍低于旧有限批次约1115 M条/s。旧有限批次读取探针未读到当前块，不能把优势解释为偷偷开启扫描。

删除发布倒计时会改变编译器生成的循环；诊断中保留一个不发布的人工倒计时也能显著改变吞吐，说明不能用“少了atomic所以一定更快”推断。人工倒计时没有用于正式测试或生产优化。能够确认的是代码路径与指令组织影响很大；没有硬件性能计数证据，尚不能确切归因于某一种CPU停顿、缓存争用或流水线瓶颈。

为什么32、64 B和16 B差很多：同配置对照表显示容量计数仅对16 B收益明显。32、64 B使用原有策略；三者原有策略的p50约1.583、1.725、2.000 ns。16 B单独加速是最终延时差距的重要来源，不能全部归因于消息长度。32 B每条复制字节是16 B的2倍，64 B是4倍；但每字节成本不线性增长，最优字节吞吐反而从15.17增至17.52、28.89 GB/s。

4 MiB块下，32 B每块容纳131072条、64 B每块65536条，每组仅1000次；换块已经是少数计时组的操作，不能继续用原来64 KiB块的“约49%组包含换块”解释新的p50。

32 B的具体未达目标：TwoBufQueue五次p50为1.708/1.750/1.750/1.750/1.750 ns；ReaderWriterQueue为1.667/1.667/1.625/1.667/1.667 ns。均值差0.083 ns、约5%，本轮不是删掉异常值造成。两者内部容量检查、游标发布和线程数不同，TwoBufQueue还保留并发第二层复制，但这些结构差异不足以证明这0.083 ns的确切硬件原因。不能宣称其无法继续优化，也不能宣称已经最低。

已试过提前推进指针、派生游标、固定长度槽位、编译器屏障、寄存器复制和编译选项等变体；未得到32、64 B稳定的额外改善，因此没有加入生产代码。部分诊断使用缩小的编译入口，其数字不进入正式对比表。业务循环为0仍有消费与回调开销；本轮正式运行写入失败和内部背压均为0。

发送、复制与排空

TwoBufQueue：Writer → 复制线程 → 第二层缓存 → 独立回调线程，逐消息调用回调。

源块 / 输出块按指标分别选择；每层数据字节预算保持不变。四种实现正式写入次数与净负载长度相同。

每轮上限按缓存的 80% / 消息字节数计算。TwoBufQueue 不扫描当前块，publish_count 为 UINT32_MAX；停止发送计时后调用 finish_block 交接当前块，再等待本轮全部回调完成。预热也在计时外交接，最终尾部统一 finish。没有增加额外消息，原生 SPSC 每条已发布，轮末无需额外交接。

本页三种长度使用相同缓存预算和业务回调循环次数；长度与Writer容量检查策略的影响另做同参数对照。

不逐条 flush · 轮末计时外交接；publish_count 固定为UINT32_MAX，当前块扫描关闭。仅预触碰写端数据页，第二层数据页没有额外预触碰。

吞吐和分组延时均在计时前准备整轮输入；每条消息的全部字都随序号变化；复制构造函数体使用一次直接 memcpy，目标成员保留 bytes{} 初始化。输入缓冲单独计算，不算队列容量，也不保证常驻 L1。

时钟、调度与限制

本机为 macOS-14.4.1-arm64-arm-64bit / arm64，Release 优化构建。

计时器：mach_absolute_time；每组 1000 次写入。组均值刻度约 0.0417 ns / 次。

写线程调度：高 QoS · 未硬绑核。调度打断和其他系统活动仍可能影响结果；复制与回调线程保留自身调度策略。

吞吐只累计写线程发送时间；排空在计时之外。并发复制 / 回调仍可能争用缓存和带宽，因此不是持续端到端吞吐。

p999 仅供观察：每次延时测量约有 9,918–9,990 个组均值样本，少于框架建议的 100,000 个。p999 的尾部覆盖有限，不能据此做稳定的尾延时承诺。p999 表示 99.9% 分位数；平均值不代表置信区间。
